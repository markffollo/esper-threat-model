TL;DR: tolink is a small URL shortener that works, but it lets strangers read, create, and misuse short links more than the README implies, and its default setup ships with weak passwords and no encryption.

  • Anyone, without logging in, can look up any short link's destination by guessing its number, and can create links that point anywhere on the web (Findings 1 and 4).
  • The shipped default passwords are weak and well known, and the database and Redis ports are exposed to the host machine (Finding 2).
  • If the default login-token secret is left unchanged, anyone can forge a valid login token for any user (Finding 3).
  • All eight findings have easy, local fixes: change defaults, add one ownership check, and tighten validation. No redesign needed.
01

Architecture & Summary

Blueprint
What tolink is, how it is built, and where the trust boundaries sit.

One app, four moving parts. A React front end talks to a Go API; the API reads and writes PostgreSQL, uses Redis to make redirects fast, and sends visitors' browsers on to whatever web address was stored. Questions a non-engineer would ask, answered from the code (not the README):

What the code actually does
Who can create a short linkAnyone, logged in or not. Guest links are not tied to any account, so nobody can manage or delete them.
Who can look up where a link goesAnyone. The lookup endpoints only check ownership if you happen to be logged in, so guests get full access (Finding 1).
What the login token protectsOnly four things: listing your own links, deleting a link, seeing your account, and changing your password. Everything else works without it.
Where links are allowed to pointAny http or https address, including addresses inside a private network. No block list (Finding 4).
Does the API fetch the target itselfNo. It only sends the visitor's browser there. So there is no server-side request forgery (SSRF) path; the risk is redirect and phishing abuse.
Are database and cache encryptedNo. The database connection is built with sslmode=disable, Redis has no password at all, and both containers publish their ports to the host (Findings 2 and 6).

Data at risk, the sensitive data that moves through the app, in plain words

  • Every long web address people shorten, some of which contain login codes or private file links
  • Account email addresses and bcrypt password hashes (good hashing, cost 12)
  • Visitor tracking per click: IP address, browser type, and the page they came from, kept forever
  • Login tokens (JWT) stored in the browser's localStorage, where any script on the page can read them (Finding 7)

Data Flow Diagram

Attack paths (High), plain-English chains: attacker action, then exploit, then access, then impact

  • Finding 1 — stranger calls the link-lookup API with number 1, 2, 3 → no login required, ownership check skipped for guests → reads every stored long address → harvests private links and login codes people shortened
  • Finding 3 + Finding 2 — attacker reads the default JWT secret from the public compose file → signs a token for any user → becomes that user → lists and deletes their links; with the default database password they may also connect directly
  • Finding 4 — attacker creates a link pointing at a fake login page → sends victims a tolink URL → victims trust the short domain → credentials phished under the service's name

Findings — STRIDE

Risk register
8 findings ranked by DREAD score. Evidence cites file:line in the clone.
Filter
Finding 1
I · information disclosureHigh

Anyone can read any short link's destination without logging in

The lookup and stats routes use "optional auth": the ownership check only runs when a token is present. A guest with no account gets the full record for any link ID, including the original long URL. IDs are simple increasing numbers, so walking 1, 2, 3 harvests the whole table. The QR endpoint is even looser: no auth and no ownership check at all, and it reveals the code for any ID.

Evidence: backend/internal/handlers/url.go:181-186 (check skipped for guests), url.go:270-275 (same in stats), url.go:170 (fetch by ID with no owner filter), backend/cmd/server/main.go:116 (OptionalAuth on the route), backend/internal/handlers/qr.go:28-37 (no auth at all). Reachable by any internet visitor.

DREAD
Finding 2
S/E · spoofing · elevationHigh

Shipped defaults: known database password and a Redis with no password, both ports open

The database password defaults to secret123 in both compose files and in the Go config fallback, and PostgreSQL publishes port 5432 to the host. Redis runs with no password and publishes 6379. Anyone who can reach those ports gets the entire link table, user emails, and password hashes, and can poison the redirect cache.

Evidence: docker-compose.yml (POSTGRES_PASSWORD: ${DB_PASSWORD:-secret123}, ports 5432:5432, 6379:6379, Redis has no requirepass), same in docker-compose.dev.yml, backend/internal/config/config.go:57 (DBPassword default secret123). Reachable from the host and, on a cloud VM, possibly the network.

DREAD
Finding 3
S · spoofingHigh

A default JWT secret in the public config means login tokens can be forged

Tokens are signed with a shared HMAC key. The key falls back to hardcoded strings when the environment variable is missing: your-super-secret-jwt-key-change-in-production in the compose file and dev_jwt_secret_key_for_local_development_only in the Go config. Both are public in this repo. Anyone who deploys without setting a real secret hands attackers the ability to mint a valid token for any user ID.

Evidence: docker-compose.yml (backend JWT_SECRET default line), backend/internal/config/config.go:63, signing at backend/pkg/utils/jwt.go:44-45 (HS256, no issuer or audience checks). Needs the default to be kept, which the README never warns about.

7.0
DREAD
Finding 4
T · tamperingMedium

Redirects go to any web address, including private network ones, with no block list

URL validation only requires an http or https scheme and a host. Anything else passes: addresses inside the company network, tracking pixels, or a fake login page. The API never fetches the address itself, so there is no SSRF into internal services from the API's network position. The real risk is that any anonymous person can register a short link under this service's domain pointing anywhere, which makes phishing look trustworthy. You asked about open redirect and SSRF specifically: open redirect is by design and unguarded; SSRF does not apply because no server-side fetch exists.

Evidence: backend/internal/services/url_service.go:89-119 (only scheme and host are checked), backend/internal/handlers/url.go:246 (302 to the stored address), guest creation allowed at main.go:110.

6.4
DREAD
Finding 5
S · spoofingMedium

The API tells every website it is OK to call it, from any origin, with credentials allowed

When the request's origin is not on a small localhost allow list, the code falls back to Access-Control-Allow-Origin: *, and it always sends Allow-Credentials: true. Browsers refuse that exact combination for credentialed requests, which limits direct account theft, but auth is Bearer tokens in headers anyway, so the safer read is: the dev-wide-open posture ships to production with no environment check, and any future cookie-based feature would be exposed immediately.

Evidence: backend/internal/middleware/cors.go:20-30, applied globally at main.go:86 with no ENV guard.

5.8
DREAD
Finding 6
T/I · tampering · disclosureMedium

The database connection is never encrypted, and the example file admits it

You asked whether sslmode=disable in .env.example reflects reality. It does, twice over: the example DATABASE_URL shows it, and the fallback DSN built from individual settings hardcodes sslmode=disable, so even a production host that offers TLS will not use it. Link data and credentials cross the network in the clear. The rest of the stack matches: nginx listens on port 80 and the default BASE_URL is http.

Evidence: .env.example:3, backend/internal/config/config.go:83 (hardcoded in the DSN), frontend/nginx.conf:2, config.go:51 (http BASE_URL).

5.6
DREAD
Finding 7
S/D · spoofing · repudiationMedium

Login tokens live in localStorage and are never revoked

The front end keeps the JWT in localStorage, readable by any injected script. On the server side there is no revocation: logout just tells the browser to drop the token, and a password change does not invalidate old tokens, so a stolen or forged token stays good for its full 24-hour life.

Evidence: frontend/src/stores/auth.store.ts:18,26, frontend/src/services/api.ts:13 (Bearer from localStorage), no deny list anywhere in backend/pkg/utils/jwt.go or backend/internal/handlers/auth.go logout path.

5.4
DREAD
Finding 8
E/D · elevation · denialLow

Visitor browsing data is kept forever, and the rate limiter trusts a forgeable header

Every redirect stores the visitor's IP, browser type, and referring page with no retention limit and no user-facing way to clear it. Separately, the rate limiter counts requests per client IP taken from proxy headers, and Gin trusts all proxies by default, so an attacker who sets X-Forwarded-For gets a fresh budget on every request. Both are abuse enablers for the open registration in Finding 4.

Evidence: backend/internal/handlers/url.go:242 (records IP, UA, referer), backend/migrations/003_create_click_stats_table.up.sql (no retention), backend/internal/middleware/rate_limit.go:51+ keyed on ClientIP() with no SetTrustedProxies call anywhere in main.go.

Recommendations

Action plan
Concrete fixes keyed to finding IDs, ordered by severity.
Filter
Finding 1 · high

Require a login on the lookup routes and filter by owner

In main.go, change urls.GET("/:id", OptionalAuth(), ...) and the stats route to RequireAuth(), and in url.go GetURL/GetURLStats make the ownership check unconditional: reject whenever shortURL.UserID is set and differs from the caller, including for guests. Add the same RequireAuth() to qr.go GetQRCode. Public redirect by short code can stay open, that is the product.

Finding 2 · high

Drop the default password and stop publishing the database and cache ports

Remove the :-secret123 and :-urlshort fallbacks from both compose files and from config.go so the server refuses to start without a real password. Delete the ports: entries for postgres and redis (the containers share a Docker network, they do not need host ports), and add requirepass to the Redis command line.

Finding 3 · high

Fail fast when no real JWT secret is set

In config.Load(), if JWT_SECRET is missing or under 32 characters and ENV=production, exit with a clear error instead of falling back to the hardcoded string. Add iss and aud claims in jwt.go and check them on validation so tokens from another service cannot be replayed.

Finding 4 · medium

Add a block list to URL validation and an abuse report route

In url_service.go ValidateURL, resolve the host and reject loopback, private, and link-local ranges, and reject hosts that look like the service's own domain. Consider requiring login to create links, or a much stricter guest rate limit, and publish an abuse contact so phishing reports can reach you.

Finding 5 · medium

Only send permissive CORS headers in development

In cors.go, gate the * fallback behind cfg.Env != "production" and drop Allow-Credentials: true, since auth is header-based and nothing uses cookies. In production, echo back only the configured frontend origin.

Finding 6 · medium

Encrypt the database connection and serve HTTPS

Change the fallback DSN in config.go:83 to sslmode=require (or verify-full with a root certificate on managed hosts), update .env.example to match, and terminate TLS at nginx so the browser-to-API leg is encrypted too. Set BASE_URL to the https address so generated short links and QR codes are correct.

Finding 7 · medium

Shorten token life and add real revocation

Cut JWT_EXPIRY_HOURS from 24 to 1, move the token to an httpOnly cookie or keep it in memory only, and add a per-user tokens_valid_after column checked in the auth middleware so logout and password change invalidate existing tokens.

Finding 8 · low

Cap click-data retention and fix the rate limiter's trust

Set router.SetTrustedProxies(nil) (or the nginx container address) in main.go, and add a job to the existing cleanup worker that deletes click_stats rows older than 30 days. Keep only a hashed or truncated IP if stats do not need the full address.

Clean surfaces: passwords are bcrypt-hashed at cost 12, all SQL goes through GORM parameter binding (no injection found), short codes use a real random source, and there are no eval or subprocess sinks anywhere in the backend. The app is not agentic, so no AI-specific threats apply.
